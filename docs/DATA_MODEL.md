# Data model

Owner: **Keanu Reeves** (design) and **Matt Damon** (migrations). Source of truth:
`supabase/migrations/`. TypeScript types are generated into `packages/core/src/database.types.ts`.

## Conventions

- **Money** is `bigint` Rappen with CHECK bounds of ±10'000'000'000 (CHF 100 million).
  `transactions.amount_rappen` is signed: negative = money out, positive = money in (refund).
- **Ownership.** Every user-owned row has `user_id` referencing `auth.users` with
  `on delete cascade`, so deleting the user deletes everything.
- **Tenant-safe references.** References between user-owned rows are composite foreign keys
  `(x_id, user_id) → x(id, user_id)`. A row can therefore never point at another user's row, even
  with a guessed id. Optional references use `on delete set null (x_id)` (only the id column).
- **Vocabularies** are `text` + CHECK constraints mirroring `packages/core/src/constants.ts`.
- **Timestamps** `created_at`/`updated_at` are set by the database (`set_updated_at` trigger;
  append-only tables get `set_created_at`, so clients cannot backdate them).
- **Periods.** A budget "month" runs from payday to the next payday: `budget_periods.starts_on`
  (inclusive) to `ends_on` (exclusive). Periods of one user can never overlap (exclusion
  constraint). A payday the month does not have (the 31st in April) falls on the month's last day.
- **Time zone.** `profiles.timezone` is a name from `pg_timezone_names` (trigger `check_timezone`).
  "Today" and the day a transaction belongs to are always taken in that zone.
- **Onboarded profiles** always have `net_income_rappen` and `payday` (CHECK
  `profiles_onboarded_has_income`): the payday reset needs both.
- **Schemas.** `public` holds the user tables and the RPCs (served by the API). `private` holds
  what no client may reach (token ciphertext, the payday reset's internals). `internal` (D-038)
  holds reference data and helpers the transaction RPCs use with the caller's rights: signed-in
  users may use it, the API does not serve it, it is read-only for them.

## Access rules

Row-level security is enabled on every table; every policy in `public` is "own rows only"
(`user_id = auth.uid()`); the reference tables in `internal` have one read-only policy for
`authenticated`. On top of RLS, table privileges start from nothing and grant only what the app
needs. Future tables also start from nothing (default privileges revoked).

`period_spending`, `remove_import_impl`, `same_merchant`, `set_transaction_splits_impl`,
`suggest_rule`, `transaction_item`, `transaction_key`, `update_transaction_impl`. `anon` executes
nothing. `roll_due_periods()` and `run_scheduled_alerts()` are for the scheduler only;
`claim_pushes` and `forget_push_tokens` for the service role (the push sender) only. Functions in
schema `private` and trigger functions are not callable by clients. Every function pins
`search_path` to `''`. Owner rights (SECURITY DEFINER) only for the reviewed
`complete_onboarding`, `delete_my_account`, `ensure_current_period`, `handle_new_user`,
`roll_due_periods` and, since M4:

- `internal.evaluate_alerts(user, transaction_ids)`: alerts are not writable by clients (a client
  could otherwise push any text to its own devices), so the engine writes them with owner rights.
  It raises 42501 unless `user` is `auth.uid()`, and every statement of `private.evaluate_alerts`
  names that user.
- `register_push_token` / `unregister_push_token`: a device that switches accounts must move its
  token to the new user, whose RLS cannot see the old row; clients get no write privilege on
  `push_tokens` at all. Both validate their input and touch only the given token and `auth.uid()`.

New functions are executable by PUBLIC by default (Postgres cannot revoke that per schema), so
every migration revokes it function by function and `privileges.test.ts` lists every executable
function.

## Transaction pipeline

`add_transactions` implements the steps of [CATEGORIZATION.md](CATEGORIZATION.md) in order, row by
row, serialized per user (advisory lock). What the database adds to that description:

- **Person's choice.** A row with a `category_id` or splits is stored as `categorized_by = 'user'`
  (confidence 100) and skips steps 5-9; re-import and deduplication (steps 2-4) still apply, so a
  manual entry can merge into a statement row and give it the person's category. `category_id:
null` (without splits) leaves the row to the pipeline.
- **Merged rows** are stored as evidence (`merged_into_id`, categorized like an added row by
  steps 1 and 5-8, never step 9). The survivor gains `merchant`, `raw_text`, `mcc`, `items` and the
  foreign amount when it has none, a `note` when it has none, and the person's category when its
  own is a guess (not `user` or `rule`, not a fixed-cost payment); what it gained is recorded in
  the evidence row's `merge_changes`. Each result describes the transaction named by
  `transaction_id` (the survivor for `merged`, the stored row for `already_imported`);
  `possible_duplicate` rows report no category. `duplicate_of` names the survivor for `merged` and,
  for `possible_duplicate`, the transaction the person sees (the survivor when the match was merged).
- **Windows** are local dates in the profile's zone, at most four days apart (steps 3 and 4),
  read through the index per (amount, source), at most the 50 nearest candidates on each side.
  The rows of the running call are skipped by source (steps 3, 4b) or data source (4a).
- **Fixed-cost payments** keep no category and `categorized_by = 'none'`; they never need review.
  Steps 5, 7 and 9 link only when none of the fixed cost's other payments is booked within 20 days
  (inclusive); step 9 also needs exactly one active fixed cost with the amount. Fixed-cost
  detection needs money out.
- **Statement rows** need an `external_id`; they are stored acknowledged and linked to the
  import's `data_sources` row. A dry run does all the work in a subtransaction and rolls it back.
- **Input bounds** beyond the table constraints, checked before any list is read: at most 2000
  rows, 50 split parts, 500 items (and 20000 bytes), 8 sources and 100 category ids in filters,
  50 fixed costs and 50 categories in `complete_onboarding` (`too_many_items`),
  unknown keys are rejected (rows, items, parts, filters, changes).

## Spending rules

What counts as spending in a period (`internal.counted_allocations`, summed by
`internal.period_spending`; the payday reset, `get_overview()`, the alert engine, the moments and
the category detail all read it):

1. A transaction belongs to the period when its booking time, converted to the user's time zone,
   falls on a date in `[starts_on, ends_on)`. 23:30 UTC on the period's last day is already the
   next day in Zurich, so it counts in the next period.
2. Ignored: deleted transactions (`deleted_at`), merged duplicates (`merged_into_id`) and
   fixed-cost payments (`fixed_cost_id`: fixed costs are already deducted in the plan).
3. A split transaction contributes its parts; any other transaction contributes itself
   (`amount_rappen`, `category_id`).
4. Counted: every negative amount (a purchase), and positive amounts that have a category (a
   refund gives money back to that category). Positive amounts without a category (e.g. a salary
   arriving through a bank feed) do not change the budget.
5. `spent = −Σ amount` per category; uncategorized spending is one total (`category_id` null).
   Categories without counted transactions have no total (0 in the overview).

When a period closes, `leftover = income − fixed costs − savings + carried over − spent` (all
categories and uncategorized), and the profile's `leftover_policy` decides what the next period
carries over (see `private.settle_leftover`).

## Alerts, moments and push (Milestone 4)

Migration `20261009090000_alerts_moments_editors.sql`; contract in [API.md](API.md#alerts-moments-reminders-editors-milestone-4).

**When the engine runs.** `private.evaluate_alerts(user, transaction_ids, now)` (owner rights)
runs at the end of `add_transactions` (with the ids of the rows stored as `added`),
`update_transaction` and `set_transaction_splits` (with their id), `remove_import` and
`set_budget` (period alerts only), through `internal.evaluate_alerts`, in the same database
transaction. The hourly pg_cron job `run-scheduled-alerts` (minute 15) calls
`run_scheduled_alerts()`: it rolls due periods, then evaluates every onboarded user and raises the
reminders (`private.reminder_alerts`). One user's failure is logged and skipped.

**Rules.** "Spent" and "balance" follow the spending rules below (`internal.period_spending`); a
category has its budget plus rollover; spendable = income − fixed costs − savings + carried over;
"today" is the local date in the profile's time zone. Each alert is inserted with
`on conflict (user_id, dedupe_key) do nothing`, so it exists at most once, also when dismissed.
Disabled types are not created (a type turned on later can still be raised while its condition
holds).

"Recent purchase": money out, booked within the last three local days, not from a statement file,
not a split, fixed-cost payment, deleted or merged. Transaction alerts carry `transaction_id`;
category alerts `category_id`; period alerts `period_id`. Texts come from `private.alert_text`
(de with Swiss spelling, en), amounts from `private.format_chf` (`CHF 1’240.50` / `CHF 1,240.50`),
dates from `private.format_day` (`18. Oktober` / `18 October`), category names from
`private.category_label` (the app's names for default keys).

**Guard (M4-06).** Statement-level `BEFORE INSERT OR UPDATE OR DELETE` triggers
(`private.guard_client_writes`) on `transactions`, `transaction_splits` and `data_sources` raise
42501 `direct_write_not_allowed` when `current_user` is `authenticated` and the setting
`batzen.via_rpc` is not `on`. The writing RPCs (`add_transactions`, `update_transaction`,
`set_transaction_splits`, `remove_import`, `acknowledge_transactions`) set it with
`set_config(…, true)` (transaction-local) and restore it before returning; an error rolls it back
with the statement. Owner rights (definer functions, foreign-key actions such as deleting a
category or the account) and the service role are not affected. The Milestone 3 bodies moved
unchanged to `internal.*_impl`; the public functions are thin wrappers (flag, call, alerts). The
flag is not a secret: it guards the REST API, which cannot run `set_config`.

**Moments.** `pending_moments()` returns at most 50 unacknowledged purchases of the last 7 local
days (not deleted, merged or fixed-cost payments), oldest first:
`{ transaction_id, amount_rappen, booked_at, merchant, source, category_id, is_split, period_id,
budget_rappen, balance_before_rappen, balance_after_rappen, remaining_before_rappen,
remaining_after_rappen, over_budget }`. "After" counts every counted part of the transaction's
period booked up to and including it, ordered by `(booked_at, id)`; "before" adds the purchase
back. `budget_rappen` = budget + rollover of its category in that period (null for a split, no
category or no budget row); `over_budget` compares the category's remaining, else the balance.
`acknowledge_transactions(ids)` (≤ 500) returns how many it acknowledged.

**Inbox.** `list_alerts({ limit 1-100 = 30, cursor, unread_only })` →
`{ items: [{ id, type, title, body, params, category_id, transaction_id, period_id, read_at,
created_at }], next_cursor: { created_at, id } | null }`, newest first, dismissed alerts left out.
`mark_alerts_read(ids | null)` (null = all unread; ≤ 500 ids) → count; `dismiss_alert(id)` →
found. 22023 `invalid_input` for unknown keys or bad values.

**Editors.** `set_budget(category, amount)` upserts the budget of the current period (rolls the
period first, waits for a running payday reset) and returns
`{ budget_id, period_id, category_id, amount_rappen, rollover_rappen }`; 22023 `invalid_amount`,
`category_not_found` (unknown, another user's, archived), 55000 `not_onboarded`.
`get_category_detail(category)` → `{ category: { id, default_key, name, icon, archived },
period: { id, starts_on, ends_on }, budget_id, budget_amount_rappen, rollover_rappen,
spent_rappen, remaining_rappen, history: [{ period_id, starts_on, ends_on, budget_amount_rappen,
rollover_rappen, spent_rappen }] (the 6 periods before, newest first), pace: { today,
days_elapsed, days_left, available_rappen, spent_rappen, daily_average_rappen, runs_out_on } }`.
Categories are inserted, renamed and archived, fixed costs inserted, changed and deactivated
through the table API (existing grants).

**Push.** `claim_pushes(limit 1-1000 = 100)` (service role) returns
`{ alert_id, user_id, type, title, body, data, sound, tokens[] }` and sets `pushed_at`: alerts
not silent, read or dismissed, at most 12 hours old, of users with a device, outside quiet hours
(local time; start inclusive, end exclusive, across midnight when start > end, none when equal),
oldest first, while the user's pushes of the local day (by `pushed_at`) stay within
`max_per_day`. Rows are locked with `skip locked`, so parallel runs never claim the same alert.
`data` = `{ alert_id, type, transaction_id?, category_id?, period_id? }`. Delivery is at most once:
a failed send is not retried (the alert stays in the inbox).

### Push delivery

The Edge Function `supabase/functions/send-pushes` (logic in `expo.ts`, unit-tested in
`supabase/tests/send-pushes.test.ts`) claims up to 500 alerts per round (repeating while rounds
are full, at most 10), sends one Expo message per alert and device to
`https://exp.host/--/api/v2/push/send` in batches of 100 (sound `default` unless the profile has
sound off), and calls `forget_push_tokens` for devices Expo reports as `DeviceNotRegistered`. It
answers only `POST` with `Authorization: Bearer <service role key>`. Environment:
`SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY` (set by Supabase), optional `EXPO_ACCESS_TOKEN`
(`supabase secrets set EXPO_ACCESS_TOKEN=…`). No secret is in the repository.

Schedule it every 5 minutes per project (the URL and key differ per environment, so this is not
a migration): store the key in Vault once, then add a Supabase Cron job (pg_cron + pg_net):

```sql
select vault.create_secret('<service role key>', 'send_pushes_key');
select cron.schedule('send-pushes', '*/5 * * * *', $$
  select net.http_post(
    url := 'https://<project-ref>.supabase.co/functions/v1/send-pushes',
    headers := jsonb_build_object(
      'Authorization', 'Bearer ' || (select decrypted_secret from vault.decrypted_secrets
                                      where name = 'send_pushes_key'),
      'Content-Type', 'application/json'),
    body := '{}'::jsonb)
$$);
```

## Changing the schema

1. Add a new migration in `supabase/migrations/` (never edit an applied one).
2. Grant privileges explicitly; add RLS policies.
3. Mirror any vocabulary in `packages/core/src/constants.ts`.
4. Regenerate types: `npm run gen:types --workspace @budget/db` (Supabase CLI output, formatted with Prettier; CI fails when the file is stale).
5. Extend `supabase/tests` (the catalog-driven tests fail until a new table is covered).
